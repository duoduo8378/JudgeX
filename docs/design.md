# JudgeX 设计文档

本文档记录 JudgeX 的设计动机、关键决策，以及开发过程中发现的两个判分系统失效场景。

---

## 一、问题定义

AI Coding 任务设计的核心难题：**如何客观判断模型产出的代码是真的解决了问题，还是只是"看起来能做对"。**

常见做法是人工阅读 diff 后给结论。这有三个难以回避的问题：

| 问题 | 具体表现 |
|---|---|
| 效率瓶颈 | 单任务数分钟，任务量难以规模化 |
| 标准漂移 | 同一份代码换人判结论不同，评测结果不可复现 |
| 判分盲区 | 拦不住"代码能跑通但实际没解决问题"的解法 |

第三点是最危险的。它意味着评测分数无法反映真实能力差距 —— 模型可能通过修改测试文件、吞掉异常、删除无关代码等方式拿到高分，而这些问题在评测中完全不被发现。

---

## 二、三层判分架构

```
候选解（模型产出的 diff）
    │
    ├─→ 静态层 Static     编译、语法、lint、类型检查
    │                    任一失败 → 0 分（一票否决）
    │
    ├─→ 结构层 Structure  diff 范围、禁用 API、AST 检查
    │                    命中违规 → 0 分（一票否决）
    │
    └─→ 动态层 Behavior   目标用例 / 边界用例 / 回归套件
                         按通过比例给分
    │
    └─→ 汇总：加权得分 + 违规标记 → 结构化判分报告
```

### 为什么是三层而不是一层

单靠测试用例（动态层）无法覆盖两类情况：

1. **代码根本跑不起来** —— 语法错误、依赖缺失，测试直接全部失败但无法区分是"答案错"还是"环境坏"
2. **代码能跑但方式违规** —— 改测试文件让断言变绿，这是纯测试无法检测的，因为测试本身就是被改的东西

单靠静态检查也不够：代码格式完美、构建通过，但逻辑是错的。

三层串联能把「能跑通但改坏了别处」和「能通过但方式违规」这两类最常见的假阳性解法一次性拦住。

### 权重设计：动态层为什么必须占绝对主导

这是本项目最重要的一个决策，且是通过实测发现的。

**最初版本**：静态 20 + 结构 20 + 动态 60，阈值 60 分

用有缺陷的实现测试，结果拿到 **61 分 —— 刚刚越过阈值，被判定为通过**。

原因很直接：缺陷实现能编译通过（静态满分）、没有违规操作（结构满分），只是行为不对。动态层扣了 30 分，但静态+结构白送 40 分，最终还是过了线。

这意味着**「能跑但错」的解法可以混进通过集**，评测结果失真。

**调整后**：静态 10 + 结构 10 + 动态 80

理由很直接：代码能编译通过 ≠ 做对了。行为正确性是判分的绝对主体，其他两层的作用是拦截和归因，不该参与分数竞争。

调整后同一缺陷实现得 46 分，正确落榜。

> 教训：否决层与给分层的设计要分离。否决层负责"是否合规"，给分层负责"是否正确"。如果否决层给的分数太高，会稀释给分层的区分度。

## 三、关键设计一：用例必须跑在候选解自己的代码上

### 问题

最初的实现里，断言直接写在用例中、引用的是参考实现：

```python
# ✗ 错误做法
def test_nested_empty():
    assert reference_parse({'a': {}}) == {'a': {}}
```

这样测的是**参考实现**，候选解交上来的代码根本没被执行。它可以完全不碰那个 bug，也能拿满分。

### 实测对比

以「修复嵌套配置空字典解析异常」任务为例，喂入一个漏改空字典分支的缺陷实现：

| 用例绑定方式 | 目标用例 | 边界用例 | 回归套件 | 总分 | 结论 |
|---|---|---|---|---|---|
| 断言引用参考实现 | 1/5 | 3/3 | 3/3 | 76 | ❌ **误判为通过** |
| 断言绑定候选实现 | 1/5 | 1/3 | 2/3 | 46 | ✅ 正确落榜 |

边界与回归用例的通过率从 100% 掉到 33% 和 67% —— 因为缺陷实现在这些场景下同样会失败。**这才是真实的判分结果。**

### 正确做法

```python
# ✓ 正确做法：断言与被测代码绑定
def case_on(impl: str, assertion: str) -> list[str]:
    return ["python", "-c", impl + "\n" + assertion]
```

在 JudgeX 中体现为 `examples/demo.py` 的 `case_on()` 函数。

## 四、关键设计二：动态层必须包含回归套件

### 问题

只测目标用例时，候选解可以通过删改无关代码让测试"变绿"。这类解法通过全部目标用例，看起来完全正确，但已经破坏了原有功能。

### 做法

动态层拆成三组用例：

| 组 | 内容 | 权重 | 拦截什么 |
|---|---|---|---|
| 目标用例 | 任务要求的新行为 | 40 | 基本要求未达成 |
| 边界用例 | 空值、极端输入、异常路径 | 25 | 只处理了正常路径 |
| 回归套件 | 原仓库既有行为 | 15 | 破坏性修改 |

回归套件兜底 —— 目标用例全过但回归挂了，说明解法有问题。

## 五、结构层的违规检测

| 违规类型 | 检测方式 | 判罚 |
|---|---|---|
| 测试文件篡改 | diff 路径匹配 `test/`、`*_test.go`、`*.spec.ts`、`Test.java` | 0 分 |
| 越界修改 | diff 超出允许文件白名单 | 0 分 |
| 禁用 API | 模式匹配（可配置） | 0 分 |
| 绕过式异常处理 | AST 识别空 `except` 块、仅 `pass`、仅 `continue` | 0 分 |
| 疑似删除既有功能 | diff 删除行数超阈值 | 0 分 |

其中 AST 检测是结构层的核心能力。纯正则只能匹配到文本模式，而空 `except` 的变体很多（`except: pass`、`except Exception: continue`、`except (A, B): pass`），AST 解析能可靠识别所有形态。

## 六、判分报告

输出结构化 JSON，便于流水线消费与留痕：

```json
{
  "task_id": "repo-a-003",
  "title": "修复嵌套配置空字典解析异常",
  "static_score": 10.0,
  "structure_score": 0.0,
  "behavior_score": 80.0,
  "total_score": 90.0,
  "violations": ["[测试文件篡改] 修改了 tests/test_parser.py，禁止通过改测试让判分变绿"],
  "verdicts": ["✓ 构建", "✓ 语法", "✓ 目标用例 5/5 (40/40)"],
  "rejected": true,
  "reject_reason": "结构层违规：测试文件篡改",
  "verdict": "结构层违规：测试文件篡改",
  "created_at": "2026-10-04T22:30:00"
}
```

`rejected` 与 `verdict` 分开：前者表示是否被否决层拦截，后者是最终结论。这样统计时可以区分「被拦截」和「未达阈值」两类不同的失败原因。

## 七、难度校准

任务难度不能靠主观判断。JudgeX 配套的校准方法：

1. 每个任务定版前，跑 3-5 个基线模型
2. 记录通过率
3. 通过率落在 20%-70% 区间才定版
4. 过高说明任务太简单，过低说明存在歧义或不可解 —— 都要改任务描述后复测

配置见 `examples/example_task.yaml` 的 `difficulty_calibration` 段。

## 八、当前实现的边界

**用例执行**：`python -c` + 退出码，零依赖但表达力有限。

**接入生产环境**需替换三处：

| 位置 | 当前 | 生产 |
|---|---|---|
| `static_check.py` | 编译 + 语法解析 | `ruff` / `mypy` / `tsc` / `mvn` |
| `behavior_check.py` | 逐条执行 + 退出码 | 解析 `pytest --junitxml` / `go test -json` |
| `structure_check.py` | 手动传入 diff | `git diff` 自动提取 |

判分核心逻辑（三层串联、权重、一票否决）无需改动。
